# 命名、来源、内部数据与 TXT

## 制作名称与双向覆盖

制作分镜决定本轮所需资产和调用名。辅助剧本、小说供事实和美术参考，不扩大本轮资产范围。只有剧本时以剧本为制作来源。内部保留每条来源的路径、集/段/镜号和行号；名称比较只清除外部 Markdown 修饰与空白，不做同义改写。

每条需要的原文叫法必须精确匹配交付主名或别名，并指向确定的资产版本。未定身份不能随意归并。“姑娘”同时指不同人物时可分别为别名，但每条需求必须由来源上下文映射具体 ID，不靠全局名称猜测。

这里的“需要”只包括角色、纯环境场景和符合特殊剧情门槛的道具。分镜道具栏中的普通茶盏、工具等只是待筛选候选，不强制创建 prop。它们用 `excluded` 加具体理由记录归属，仍算完成名称核对，不能为了追求映射数量而扩大独立道具库。场景中的角色名称与动作必须剥离；名称映射不意味着把角色画进场景。

名称相同、实体不同允许分条；同一实体、版本不同也允许主名相同。内部 `id` 唯一，`entity_id` 表示同一个实际实体，`variant` 显式区分制作版本。角色版本写在第三行的 `造型版本：`；场景和道具使用 `版本：`。不得将内部 ID 拼入交付名称。

人物无名时采用来源实际用过的称谓，例如“黑衣刀客”；来源只有行为描述时从原句截取真实称谓，不能编姓名。确实无法提取稳定称谓时列为命名待定，交付已完成部分并说明，不能宣称全量匹配。不能把小说独有的名号当作分镜实际叫法。

每条交付资产都要有至少一条制作来源引用，不可只凭小说补出生产资产。每个引用记录来源文件和行号，且该行须出现主名或本条明确别名。跨行指代时引用含称谓的行，并在内部解释指代链。

复用历史资产时保留认可的外观与声线，新增本轮实际叫法作为别名；若历史设定与新来源冲突，列具体差异。没有历史资产就说明本轮仅完成当前材料内去重，不必强制追问。

## v2 内部契约

内部使用下列对象；通过 Python 内存或 UTF-8 标准输入传给脚本。默认不写 JSON 文件，不把结构化对象作为最终交付。允许多行缩进，无单行限制。

```json
{
  "schema_version": 2,
  "assets": {
    "role": [],
    "scene": [],
    "prop": []
  },
  "requirements": []
}
```

每条资产：

```json
{
  "id": "role-001",
  "entity_id": "person-001",
  "name": "阿月",
  "aliases": ["姑娘"],
  "variant": "基础",
  "description": "按类型规范编写的完整交付描述",
  "sources": [{"source": "分镜.md", "line": 12}]
}
```

`source` 用本次工作目录可解析的文件路径，建议绝对路径；`line` 从 1 开始。各类均为数组，避免字典同名键覆盖。角色支持 `kind: "group"`、`kind: "voice"`；默认单体。内部可增加 `design_notes`、`continuity` 等推断与美术记录，不导出到 TXT。

每条 prop 还必须包含：

```json
{
  "importance": {
    "category": "身份信物",
    "reason": "原文明确双鱼玉佩是母亲留下的认亲信物",
    "sources": [{"source": "分镜.md", "line": 18}]
  }
}
```

类别限 `身份信物`、`关键证据`、`特殊能力物件`、`剧情关键物件`、`用户指定`。具体作用与依据必须真实；一般使用、递交、破坏、连续持有不能单独作为特殊作用。证据行应出现本物的主名或别名，跨行指代时同时附上含名称行与实际关键用途行，由人工核对指代链。`importance` 不导出进视觉提示词。旧版字典无法表达该依据，含道具时必须补为 v2 后才能导出。

每条需求：

```json
{
  "type": "role",
  "name": "姑娘",
  "source": "分镜.md",
  "line": 12,
  "status": "mapped",
  "asset_ids": ["role-001"]
}
```

`mapped` 默认指向唯一具体 ID，并精确命中其主名或别名。同一行确实明确需要多个形态或多名同称谓实体时，可列多个 ID，并必填 `usage` 解释同时需要哪些版本及依据，例如“此行明确由鸟形态变为凤凰，两版本均需制作”；每个目标都须有匹配主名/别名。多个 ID 不能表示“还没确定选谁”。`excluded` 须写 `reason`，用于纯提及、背景陈设、已并入角色服饰等真实排除，不可用来绕过必需资产。`pending` 须说明原因，校验失败，不能声称完整交付。

## 脚本用法

```text
python -B scripts/parse_storyboard.py "分镜.md"
python -B scripts/check_assets.py - --source "分镜.md"
python -B scripts/to_txt.py - "项目_资产_20261024" --source "分镜.md"
```

后两个命令的 `-` 从标准输入读取内部数据。调用者也可 `from assets_core import validate, export_txt` 直接传对象。多个制作文件重复指定 `--source`。辅助小说不传给 `--source`，避免把参考角色误纳入强制覆盖范围。

`--source` 会复扫制作文件，核对显式人物/场景/道具栏的每项都有需求处理记录，验证每条需求名称确实出现在对应行、每条资产都引用指定制作源。脚本不会可靠识别所有自由叙述中的隐含物件，必须通读补齐需求后人工复核。扫描结果的 `diagnostics` 是待查项；不能忽略有损解析告警。

旧版 `role/scene/prop` 字典可用旧文件作为输入转换处理，检查时明确警告其缺失实体、版本和来源信息；启用 `--source` 必须使用 v2，不能以旧数据宣称分镜对齐。

## 校验与导出

- 结构检查：类型、重复键、重复内部 ID、字段非空、角色五行六项、场景道具标签、各记录与正文名称/别名/版本一致、分隔符冲突。
- 范围检查：场景明确无人物、无动物，检查正向角色、影像和动物出现；独立道具必须有有效 `importance` 与来源，普通道具候选可按理由排除。
- 来源检查：原始需求及资产来源行、明确名称覆盖、映射的类型与具体版本、禁止未处理需求；指定来源时全量核对显式栏。
- 人工检查：实体是否同一、场景是否真正无角色、道具是否确有特殊剧情作用及证据指代是否成立、外貌硬特征、设计是否改变剧情、群像人数、美术完成度、自由叙述漏项及连续性。文字检查不是完整的语义理解，不能仅凭无人物声明或 importance 自填标签视为全部通过。
- 长度不足仅警告，不用“至少两种面料/四种材质/六件陈设”强迫新增设定。未设定等占位句应完成补足或列待定；“无发饰”“素面无纹样”“无对白”属于有效明确状态。
- 导出前自动校验。输出目录必须不存在或为空，防止混入旧版文件；已有交付换新目录，保留原包，不自动删除旧文件。
- 只导出 description，程序已验证其中含名称、别名和版本。顺序按输入数组，建议按首次制作出现排序；同实体的版本可紧邻。
- 生成后重新读取 UTF-8 TXT，核对段数和正文；只产生三类 TXT，空类型不建文件夹，首尾无 `@`，每条资产内部不允许独立一行 `@`。
- 检查失败返回非零且不导出。通过只证明列明的自动检查，不能宣称故事覆盖和审美喜好已由机器证明。
